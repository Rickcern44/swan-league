**Product source of truth:** [docs/reference/Swan League App — Product Requirements.md](reference/Swan%20League%20App%20—%20Product%20Requirements.md). Scope and phasing live there (§11); this page only tracks delivery against it.

## Where we are

Phases 0 and 1 are implemented in code. Phase 2 (admin week workflow and simulation) is next, then Phase 3 (coach picks) and Phase 4 (notifications).

Evidence levels used below:

- **Implemented**: code and tests exist. `dotnet test Swan.slnx --no-restore` passed 148 tests (Core 65, Services 16, Architecture 62, API 4, Worker 1).
- **Accepted end to end**: the full Aspire stack and Playwright flows have been run against the exit criteria. Not yet done for any phase: no Aspire-stack or Playwright run has been recorded.

| 2. Admin week workflow, scores import, simulation | In progress. Admin week lifecycle API (`/api/admin/weeks/{weekId}`) is built, and per-game line history is persisted so a line can be added and later approved via `lines/approve-latest`. Admins can record manual game results on a locked week, finalize it, and recompute `WeekScore`s (`/games/{gameId}/result`, `/finalize`, `/recompute`; regular-season weeks only, default scoring settings because none are persisted). `POST /api/admin/seasons/{seasonId}/weeks/recompute` rescores every Final regular-season week of a season on demand (used to correct weeks scored before dog points became Dog-pool-only). A draft week's dog list can be generated from approved lines (`/dog-options/generate`; spread is home-perspective, so +x makes the home team the dog, -x the away team) or replaced by an admin (`PUT /dog-options`). A season can be created (`POST /api/admin/seasons`) by a global administrator or by a user with an active Commissioner membership of any season, and by nobody else: a coach, an inactive commissioner, a deactivated user and an unknown user get 403 `season.creator-forbidden` (an anonymous or forged-cookie caller gets 401) and nothing is written. The check is made in the service from the database, not from claims, under share locks on the user and membership rows inside the same transaction as the insert, so someone deactivated at that moment cannot slip through; the creator becomes the season's commissioner and the one-Setup-season rule is unchanged. The Setup routes (`/api/admin/seasons/setup/...`, including finishing and starting) are open to a global administrator or to the active commissioner of the season that is in Setup, checked against the database on every request (so losing the membership ends the access at once); a commissioner of any other season, a coach and anonymous callers are refused (403/401), and the expansion applies to no other administrative route (the dashboard, audit log and week actions stay Admin-only). Starting still needs the season's own commissioner, so an administrator who is not the commissioner can configure and finish a season but cannot start it. `GET /api/me` also answers `setupAccess` (`manage` for an administrator or the commissioner of the Setup season, `create` for an active commissioner while no season is in Setup, otherwise `none`) and `commissionsLiveSeason` (an active commissioner of the newest live season), both read from the database on each call; the app uses them to give a commissioner whose global role is Coach the Season setup and Roster draft pages (a Coach with `none` still sees only their own picks and roster, and an administrator keeps both pages whatever the flags say). An admin can create one blank Setup season (`POST /api/admin/seasons`, `GET /api/admin/seasons/setup`): PRD default $100 buy-in split Main 60 / Dog 20 / Regular Season 10 / Playoff 10, three double-dog weeks, Sunday 1:00 PM ET deadline; year, name and simulation flag come from the caller and can be revised while the season is in Setup (`PUT /api/admin/seasons/setup`). The buy-in and the four fixed pool stakes can be revised too (`PUT /api/admin/seasons/setup/money`): all USD and positive, stakes must add up to the buy-in, pool names are fixed, and each real change writes a `season.setup.money.updated` audit entry (identical replays write none). Edits take a row lock and run in the retrying execution strategy so they cannot race activation. The weekly team-pick deadline (Eastern `TimeOnly`, JSON `"HH:mm:ss"`, body `{"teamPickDeadlineEastern": "11:30:00"}`) can be revised too (`PUT /api/admin/seasons/setup/deadline`; missing, null or malformed is 400): it returns from `GET /api/admin/seasons/setup`, feeds `LockPolicy.WeekDeadline`, and each real change writes a `season.setup.deadline.updated` audit entry (replays write none). Double-dog weeks were first only an aggregate count (`DoubleDogWeeks`); the wizard now persists the actual week numbers (see the sixth wizard page below). The admin landing page now shows this as a six-page Season setup wizard (start a season, then Basics, Money, Weekly deadline, Teams and point values, Schedule import and Weeks and dogs, each with Back and, except Schedule import before it has an import, Save & continue, saving through its endpoint). The season stores a Setup-only resume step (`SetupStep`: Basics, Money, WeeklyDeadline, TeamsAndPoints, ScheduleImport, WeeksAndDogs, FinesAndPayouts; new and pre-existing seasons open at Basics), returned on the Setup summary and saved with `PUT /api/admin/seasons/setup/step` (`{"step": 1}`; unknown or missing step is 400, replays write no audit, real changes write `season.setup.step.updated`). A successful save records the next page as the resume point without ever moving it backwards. The fourth page, Teams and point values, lists the 32 canonical teams by division (`GET /api/admin/seasons/setup/teams`) and saves a prior-season finish for each (`PUT /api/admin/seasons/setup/teams`, body `{"teams":[{"teamId":…,"finishPosition":1}]}`): exactly the known teams once each, finishes 1 to 4, one team per finish in every division, with the point value derived as the finish (no point-value input). Rows are `SeasonTeam` rows of the Setup season only, replaced as one set under the same row lock, with `season.setup.teams.updated` audited on real changes only; the database enforces one row per (season, team) and per (season, division, finish) (the migration refuses to run if existing rows already break either rule). Saving records Schedule import as the resume point and opens that page. The fifth page, Schedule import, fetches the Setup season's regular-season NFL schedule from BALLDONTLIE on demand (`POST /api/admin/seasons/setup/schedule/preview`; the server reads every cursor page with `seasons[]`, `season_types[]=2` and `per_page=100`, using the key from `ExternalServices:BallDontLie:ApiKey`, a .NET user secret in development, sent only in the `Authorization` header and never returned or logged). A preview saves nothing and lists the games by week with kickoffs shown in Eastern time; the server holds the validated preview in memory for 15 minutes. Confirming (`POST /setup/schedule/import` with the preview's fingerprint) imports exactly that preview without calling the provider again, as regular Weeks 1 to 18 with their Games (each carrying the provider game id, unique across the database) in one transaction under the Setup row lock, and writes a `season.setup.schedule.imported` audit entry recording the provider, season, fetched and imported times, counts and fingerprint (the raw response is not stored). It refuses, changing nothing, when the provider is not configured or has no games, a week is outside 1 to 18 or any of weeks 1 to 18 has no games (a partial schedule is never imported), a provider game id repeats, a team is unknown or not in the season's team list, a kickoff cannot be read, or the season already holds an imported schedule; an unpublished season is a valid empty preview. `GET /setup/schedule` reads only the saved schedule. The manual CSV importer, background refresh, odds/lines/results imports and replacing an imported schedule remain out of scope; The sixth page, Weeks and dogs, reads only the imported schedule (`GET /api/admin/seasons/setup/double-dog-weeks`: all 18 weeks, each with whether it is selected, required or suggested, and reason text; 409 `schedule.missing` until a full schedule is imported) and saves the administrator-confirmed selection (`PUT` the same path, body `{"weeks":[2,12,17]}`): unique regular-season weeks 1 to 18, exactly 3 or 4, always including Week 2 (R7), else 400 `season.double-dogs` with the reason and nothing changed. Week 2 is required; the weeks containing U.S. Thanksgiving (fourth Thursday of November) and December 25, judged by game kickoffs in America/New_York against the imported schedule's own year (not the Setup year, which can still be edited after an import), are only suggested, and may overlap each other or Week 2. The selection is persisted on the season (`DoubleDogWeekNumbers`; existing seasons keep an empty selection, none is invented), `Settings.DoubleDogWeeks` is kept equal to its count, a real change writes a `season.setup.double-dogs.updated` audit entry (replays none) under the same row lock, and `Season.Activate()` now fails unless a valid selection is saved. Saving records Fines and payouts as the resume point (never moving it backwards). The seventh page, Fines and payouts, configures a missed-pick fine and per-pool payout plans, and calculates only: no money moves and nothing is assessed or settled. A new season starts with a $5.00 fine and no plans; seasons that predate it stay unconfigured (null fine, empty plans) and are given no invented choices. `GET /api/admin/seasons/setup/fines-and-payouts` returns the saved configuration and a calculator over this season's ACTIVE coach memberships only (administrators, commissioners and inactive memberships are not counted): per pool, pot = stake x active coaches, and each placing's amount, where every placing except the lowest is its percent of the pot rounded down to the cent and the lowest takes the remainder, so the amounts always add up to the pot exactly. `PUT` the same path saves everything together or nothing (body `{"missedPickFine":5,"payouts":[{"pool":"Main","places":[{"position":1,"percent":70},{"position":2,"percent":30}]},...]}`, exactly the four pools once each; the fine positive, USD and whole cents; unique positive positions; percentages above zero with at most two decimals totalling exactly 100.00 per pool; otherwise 400 `season.payouts` with the reason and nothing changed), under the Setup row lock, auditing `season.setup.fines-and-payouts.updated` only on a real change. Saving records League settings as the resume point (never moving it backwards). The eighth page, League settings, saves the three owner-controlled rules (`GET`/`PUT /api/admin/seasons/setup/league-settings`, body `{"teamMayAlsoBeDog":true,"pointColors":[{"points":1,"color":"Green"},...],"recordHolder":"FirstOccurrence"}`): R17 (a team may be both a started team and the same week's dog; default on), R18 (a one-to-one mapping of the point values 1 to 4 to green, blue, yellow and red; default 1 green, 2 blue, 3 yellow, 4 red) and R19 (who holds a Going Perf or 0fer record, `FirstOccurrence` by default or `MostOccurrences`). They are stored inside the season settings value (`SeasonSettings.Rules`; seasons saved earlier load the defaults and keep every other field), saved atomically in Setup only under the same row lock, and a real change writes a `season.setup.league-settings.updated` audit entry with the old and new values (replays none); a mapping that is not exactly four points and four colors once each, an unknown record mode or a missing field is 400 `season.league-settings` and changes nothing. What uses them today: R17 now reaches scoring, because finalizing or recomputing a regular week reads the season's setting (completed weeks are not re-scored automatically; a recompute applies the rule as it then stands). R18 and R19 are saved only; the tiebreaker and records features that will read them are not built. The page also lists R1 to R16, R20 and R21 as fixed. Saving records Coaches as the resume point (never moving it backwards). The ninth page, Coaches, prepares the Setup season's coach list and nothing else (`GET`/`PUT /api/admin/seasons/setup/coaches`): `GET` returns the season's Coach memberships (active and inactive), the most recent earlier season (newest non-Setup season by year, then state, then id) and its active coaches as carry-forward candidates (never copied automatically), and the active count; `PUT {"coaches":[{"email":"...","name":"..."}]}` takes the complete desired active list, where every email must be valid and unique (trimmed, lowercase) and every name non-blank (else 400 `season.coaches` naming the row and nothing changes; an empty list is allowed). A person is matched by email and reused as is (their name and global role are never changed); only an email nobody has becomes a new user with the Coach role. Under the Setup row lock, listed people get an active Coach membership for the Setup season (a former one is reactivated), unlisted active Setup-season Coach memberships are made inactive (never deleted), and no other season's membership and no administrator or commissioner membership is touched; naming a deactivated person, or someone who is already an administrator or commissioner of the Setup season, or an email that two people share, is a 400. A real change is audited as `season.setup.coaches.updated` with the before and after membership states (an identical list writes none). It sends no email or invitation, creates no roster and does not open the roster window. The payout calculator's active-coach count reflects the saved list. Saving records Review and create as the resume point (never moving it backwards). The tenth and last page, Review and create, summarizes everything saved and finishes the wizard without activating anything (`GET /api/admin/seasons/setup/review`, `POST /api/admin/seasons/setup/review/finish`; admin only; nothing calls the schedule provider or any other service). The read model is built only from saved data: basics, pool stakes and fine and payout plans (with the calculator), the deadline, how many teams have a division finish, the imported weeks and games, the double-dog weeks, R17 to R19, and the active-coach count. Readiness is derived on the server. Blockers (each with the wizard step that fixes it): the name and year, pool stakes that do not add up to the buy-in, incomplete teams and point values, anything short of a complete 18-week imported schedule, an invalid or unsaved double-dog selection, and an unsaved or invalid fine and payout plans. Warnings do not block: zero active coaches, a holiday week the schedule suggests as a double-dog week that is not selected, and a season year that no longer matches the year of the imported schedule. `POST .../finish` re-checks the blockers under the Setup row lock and answers 409 `setup.incomplete` without touching anything if any remain; when ready it records the new completed state (`SetupStep.Completed`, reachable only through this action, never by saving a step) and writes one `season.setup.completed` audit entry with a compact summary, and repeating it writes nothing. Once finished, a lower step sent later (a stale page or a direct caller) is ignored, so the completed state is never lost by accident. The season stays in Setup: finishing does not activate it, archive anything, send invitations or email, open the roster window, create rosters or picks, or process payments, and no other season is touched. A season that was finished and later loses something still reports completed, lists the new blockers, and cannot be finished again until they are fixed. Activation, the roster window and inviting coaches by email are not built. Fine amount, payout splits, double-dog week numbers and playoff settings (the rest of the wizard) remain. Only one Setup season can exist, enforced by a partial unique index (`ux_seasons_single_setup`); the migration refuses to run if duplicate Setup seasons already exist and never deletes or merges them. The admin landing page is now the Week Dashboard inside a main app shell (`GET /api/admin/dashboard`, admin only, read-only: no provider calls and no writes). The server picks the Live season (if several are Live, the newest year wins, then the name, then the id) and derives its current week and a ranked attention list from saved data only, counting only included (non-excluded) games. The current week is the lowest-numbered Draft, LinesApproved or Open week, else the lowest Locked week, else the newest Final week. Attention items have a stable `kind`, human reason, week id, number and state, a count and whether they need a decision: the next Draft week asks for approved lines (`lines-missing`, then `lines-ready` when every included game has one, or `week-empty`); a LinesApproved week is `publish-ready`; an Open week is informational (`picks-live`); a Locked week is `results-missing` or, when every result is in, `finalize-ready`. Decisions rank before information, then earlier weeks before later ones, so an earlier non-final week outranks a newer current week. A season whose weeks are all Final reports caught up and invents no task; no Live season returns a successful empty state that points to Season setup. The shell has a skip link, labelled landmarks and a primary navigation (bottom bar on phones, left rail from 56rem); Week and Standings are shown as "Coming soon" text, not links, and Season setup is at `/setup`. Coaches get a calm placeholder home and never call an admin endpoint. The dashboard has no actions yet: items are not links because the pages they would open do not exist. The Week Workspace (`/weeks/<weekId>`, admin only) is where an administrator works one week end to end in the browser: dashboard attention rows and the current-week summary link to it. It loads `GET /api/admin/weeks/{weekId}` and reuses the existing lifecycle endpoints without re-implementing their rules; every response now has a readable shape (plain Guid ids, string `kind`/`state`, per-game `homeTeamName`/`awayTeamName` from the team catalog or the label "Unknown team", games in kickoff order, included/approved/result counts, and a server-derived `nextAction` with `kind`, `label`, `detail` and `canAct`). Draft: add or edit a line (explicit Save line or Save and approve), approve the latest line, and approve all lines only when each included game's latest line is approved (the server refuses `ApproveLines` while a newer unapproved line exists, so an old spread can never be frozen; the dashboard and next action name those games instead). LinesApproved: publish. Open: lock. Locked: enter a result per game, then finalize once none is missing. Final: scores shown, recompute offered. A rejected action shows the server's reason beside the action and leaves the page as it was; nothing is reported as saved unless the server accepted it. Phone has one editor open at a time and a sticky action dock above the bottom navigation; desktop adds a Week pulse column. Coaches never load or call admin week data. The shared visual foundation (ink, ice and brass tokens, serif display numerals, one feather mark, hairline dividers, text-labelled state chips) now covers the shell, dashboard and workspace; the Season setup wizard keeps its older card styling. Input safeguards (a lead assumption recorded on 2026-10-15 because the decision wake elapsed with no reply from the person; revisit if they disagree): a spread must be from -30 to 30 inclusive and a result score a whole number from 0 to 100 inclusive. The server is authoritative (`Spread.Create` and `GameResult.Create`; out-of-range answers 400 with `spread.invalid` or `game-result.invalid`); the editors refuse the same values, and forms such as `1e3`, `0x10`, `3,5` or fractions, before sending anything. Recompute asks for an explicit confirmation in the dock (Confirm recompute or Cancel, Escape cancels) before the existing endpoint is called; publish, lock and finalize still have no confirmation step. Not in scope and not built: dog options in the workspace, abbreviations (the catalog has none, so full names are shortened to the nickname), reopening a Final week, and confirmation steps before publish, lock or finalize. Scores import and simulation remain. **Season-start wizard (four milestones).** The ten saved sub-steps are presented as four milestones in contiguous runs, because the saved step never moves backwards: League foundation (Basics, Money, Weekly deadline), Schedule and scoring (Teams and point values, Schedule import, Weeks and dogs), People and payouts (Fines and payouts, League settings, Coaches) and Ready to launch (the last page, formerly Review and create). Every setup API and the saved resume step are unchanged. Reached milestones are buttons (completed work stays editable), later ones are plain text, and when the person is away from the resume point a Next up line offers Continue setup. A schedule import is shown as one summary line with the games behind a Review games by week disclosure. Ready to launch lists blockers first, then compact summary cards with Edit buttons and a View all details disclosure, then the one final decision: a roster draft deadline (Eastern Time) beside an Open roster draft button, which opens a confirmation (Escape or Cancel closes it, focus moves in and back) saying that coaches lock their nine teams by the deadline and after that only the commissioner can correct a roster. In one transaction it empties the season-scoped tables (seasons, memberships, rosters, ballots and picks, schedule weeks, games and dog options, scoring, money, notifications, notification preferences, push subscriptions and announcements, audit entries) and keeps the 32-team catalog, users, login tokens, sessions, scheduled jobs (notification preferences and push registrations belong to memberships, so they are cleared with them); it then writes one `development.season-data-reset` audit entry. Sessions are untouched, so nobody is signed out. `GET /api/me` answers `developmentTools` (true only for an administrator in Development), and the Season setup page then offers a Development tools disclosure with a confirmed Reset local season data action; afterwards there is no Setup season and the page shows the Start a new season form. | 3. Coach picks | In progress. **Roster draft period (commissioner-controlled).** A season now starts in a roster draft. Whoever creates a season becomes its commissioner (an active `Commissioner` membership; the global Admin role alone confers nothing, and the development seed makes the seeded admin the commissioner). Once Setup is finished (`Finish setup` is unchanged and still activates nothing), the commissioner starts the season from the review page (`POST /api/admin/seasons/setup/activate`, body `{"rosterDraftDeadlineEastern":"2026-10-20T18:00"}`): the deadline is an Eastern wall-clock time resolved to a stored instant (`Season.RosterDraftDeadline`); a time the clocks skip or repeat, a missing time, one in the past and one more than a year away (or in a year outside 1900 to 2200) are 400 `season.draft-deadline`, a caller who is not the season's commissioner is 403 `commissioner.required`, a season with no active commissioner is 409 `season.commissioner`, and an unfinished or no-longer-ready Setup is refused. A valid start sets the season Live, opens the draft until the deadline and writes a `season.activated` audit entry. Until the deadline an active coach (role Coach, active Coach membership of the newest live season) opens `/roster` (`GET/PUT /api/coach/roster`, `POST /api/coach/roster/lock`; admins get 403): a save is exactly nine distinct teams of that season (400 `roster.count`/`roster.duplicate`/`roster.team`), is revision-checked (409 `roster.stale`, `season.stale`) and transactional under a row lock on the coach's membership; an explicit lock needs exactly nine teams, takes effect at once (even before the deadline) and cannot be repeated. After the deadline, or once locked, the coach gets 409 `roster.locked` and server time (not the browser) decides. An incomplete roster is never filled or locked for the coach: after the deadline it stays incomplete and the Pick Desk refuses weekly picks for it (`roster-incomplete` / 409 `roster.incomplete`) until it has exactly nine teams. Only the season's commissioner may correct a roster (`GET /api/commissioner/roster-draft`, `POST /api/commissioner/roster-draft/corrections`; authority is an active Commissioner membership of the newest live season, so a coach, an administrator who is not its commissioner, another season's commissioner and anonymous callers are refused with 403/401): one action, allowed before or after the deadline and on locked rosters, replaces one team with another or adds a team to a short roster, needs a non-blank reason, is revision-checked and writes a `roster.corrected` audit entry with the actor, the coach, the before and after rosters, the reason and the time. When a correction removes a team, that team's picks are also taken off the coach's ballots for weeks that are Open or Locked (the coach's ballot revision moves on, the ballot records why, and a `ballot.pick-removed` audit entry is written with the reason); a finished week's ballot and scores are left as they were, and dog picks are not roster-limited so they stay. Rosters are now one per coach and season (`ux_rosters_membership_season`) with a revision, lock flag and lock time; the migration refuses to run if duplicate rosters already exist. A season started before this has no deadline, so its draft counts as closed and its existing rosters keep working. Not built: invitations or reminder emails, autopick, draft order or snake draft, team exclusivity across coaches, roster history, and a way to reopen a closed draft. The Coach Pick Desk lets a signed-in coach (role Coach with an active Coach membership in a live season; administrators are refused with 403) make and revise their own regular and dog picks for the open regular week. `GET /api/coach/picks/current` returns the desk: the season and week (the lowest-numbered Open regular week of the newest live season), the weekly deadline, the coach's own roster teams that play with their point value (the season division finish, R3), each team's lock time (the earlier of kickoff and the weekly deadline, R6/R20), the week's published dog options with their spread and kickoff lock (R8), the coach's saved selections, and a ballot `revision`. `PUT /api/coach/picks/current` (`{weekId, expectedRevision, teamIds, dogTeamIds}`) saves the whole editable ballot at once under a row lock on the coach's membership: at most 3 different roster teams that play, one dog (two in a double-dog week, from different teams and games, R7/R16), a selection whose game has locked can be kept but never added, changed or removed, and a stale revision or week is refused. Refusals are stable codes with readable messages and change nothing: `pick.invalid` and `dog.invalid` answer 400; `pick.locked`, `dog.locked`, `ballot.stale`, `week.stale` and `pick.unavailable` answer 409. A coach with no membership, no open week or no roster teams gets a calm empty state, not an error. Only the acting coach's own ballot is ever read or written; other coaches' picks are not exposed (R21 visibility is not built). Rosters now persist their nine teams (a uuid[] column), the database allows one ballot per membership and week (`ux_ballots_membership_week`; the migration refuses to run if duplicates already exist) and each ballot carries a `Revision`. The development seed gives each seeded coach nine teams and publishes Week 2 (a double-dog week) with approved lines and dog options. Roster drafting, other coaches' picks, standings, notifications and fines, playoffs and automatic missed-pick handling are not built. | — |
